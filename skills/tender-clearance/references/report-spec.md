# 报告规范（report-spec）

## 输出物

| 文件 | 性质 |
|---|---|
| `output/清标结果.json` | 结构化全量结果（验收基准，Schema：schemas/report-bundle.schema.json） |
| `output/清标报告.md` | 审阅版 Markdown（验收基准，模板：templates/清标报告.md.jinja） |
| `output/证据索引.csv` | 证据登记表（utf-8-sig） |
| `output/人工复核清单.csv` | I 级/主体歧义/低置信度/读取失败/覆盖缺口（utf-8-sig） |
| `output/清标报告.pdf` | Markdown 同源审阅副本（report 核心档位） |
| `output/清标报告.docx` | `review` / `workpaper` 档位可选展示副本（python-docx） |
| `output/清标底稿.xlsx` | `workpaper` 档位可选工作底稿（openpyxl/Node runtime） |

Markdown 和 JSON 是验收基准；PDF、DOCX、Excel 是按档位派生的展示/工作底稿副本。
档位副本写入 `output/exports/<profile>/`；报告运行不触发 OCR 或外部网络查询，
但渲染前必须确认本次 SRM 查询门禁已通过。

## 固定章节

1. **封面信息页**：招标人、项目名称、项目编号、投标日期和投标人名单。
2. **基本信息页**：采购项目信息及商务标投标人主体字段。
3. **工商信息**：按投标人展示 SRM 工商字段和重复校验结论。
4. **股东信息**：按投标人展示股东字段和重复校验结论。
5. **分支机构**：按投标人展示企业名称、成立日期、状态、法人和重复校验结论。
6. **主要人员**：按投标人展示姓名、职位和重复校验结论。
7. **政府采购网**：按供应商名称查询失信信息，并直接展示已导入的证据截图。
8. **文件线索**：PDF、Office 与扫描件的文件属性、编辑痕迹和扫描设备线索。
9. **清标结论**：可复核、可追溯、按 I/II/III 三级预警展示。
10. **证据与人工复核**：证据索引、查询状态和待补资料。

## 每条风险明细行的必备字段

`编号`、`风险域`、`预警级别`、`证据强度`、`涉及供应商`、`发现事实`、`规则编号`、
`证据定位`、`查询/采集时间`、`状态`、`建议复核动作`。

## 表述红线

- `redaction_mode: none` 时按用户授权显示完整身份证号和手机号；`standard` 时显示掩码和受控摘要；
- 弱线索（META-003、ID-003W、META-001 III）事实文本必须中性
  （“存在弱同源线索……仅作为线索列出”），禁止出现“同一制作方”“串标”“围标”“违法”等断言；
- 查询状态如实展示；不得出现“无失信”“未发现风险”替代未完成查询；
- 所有 I 级与主体歧义项标注“人工复核必需”。

## 渲染前检查（render_report.py 自动执行）

1. Schema 校验：ReportBundle 按 schemas/report-bundle.schema.json 构造，失败即退出；
2. `redaction_mode: standard` 时对验收基准输出扫描完整身份证号/手机号模式；
   `none` 时不执行该检查，但仍禁止密码、Cookie 和令牌进入输出。

## 验收标准（对应方案 9.3）

1. 四类正文（公司交叉、文件属性、司法经营、违法失信）和查询覆盖表均存在；
2. T02、T04、T07 的结果、级别与人工复核要求正确；
3. T03 和 T08 不被表述为违法或串标事实；
4. 任一发现可凭证据 ID 回到证据索引和原始文件定位；
5. `redaction_mode: standard` 时没有完整身份证号、手机号；任一模式都没有访问凭证；
6. SRM 登录成功但无匹配信息时仍能输出报告，并如实记录 `no_result`；
7. 规则等级漂移、未标识查询失败、无法追溯或敏感信息泄露 —— 任一出现即不通过。
