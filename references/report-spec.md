# 报告规范（report-spec）

## 输出物

| 文件 | 性质 |
|---|---|
| `output/清标结果.json` | 结构化全量结果（验收基准，Schema：schemas/report-bundle.schema.json） |
| `output/清标报告.md` | 审阅版 Markdown（验收基准，模板：templates/清标报告.md.jinja） |
| `output/证据索引.csv` | 证据登记表（utf-8-sig） |
| `output/人工复核清单.csv` | I 级/主体歧义/低置信度/读取失败/覆盖缺口（utf-8-sig） |
| `output/清标报告.docx` | 可选展示副本（python-docx 生成） |

Markdown 和 JSON 是验收基准；DOCX/PDF 是展示副本（PDF 需要额外渲染依赖，暂缺）。

## 固定章节（11 章）

1. **封面信息页**：只列示有封面第一页证据的招标人、项目名称、项目编号、投标日期和投标人名单。
2. **基本信息页**：采购项目字段和商务标投标人字段；技术标、一览表不参与主体识别。
3. **项目、范围与结论使用说明**：项目名称、投标截止日、参与供应商、运行时间、版本、
   资料范围、查询覆盖和限制；**必须包含结论边界声明**（风险线索整理，非最终认定）。
4. **执行摘要与预警总览**：每家供应商 I/II/III 级数量、未完成查询数、必须人工复核项；
   数量合计不得描述为违法数量；附查询覆盖矩阵与 I 级首页提示。
5. **公司信息交叉检查**：信用代码、电话、邮箱、地址、法定代表人、授权代表、股东、联系人
   供应商两两对照矩阵，共同值标注“共同”，附证据定位指引。
6. **投标文件属性风险检查**：同源线索明细（编号/预警/强度/供应商/事实/规则/状态/建议动作）；
   附属性读取说明（三类信息边界）。
7. **SRM 企业信息**：按供应商列示工商信息、股东、分支机构、主要人员；每一项分别输出交叉校验结果。
8. **股权关系与司法经营风险**：关系表（含比例、起止日期、主体确认）、司法记录表、
   相关发现明细。
9. **违法失信信息**：按渠道列示查询状态与命中记录（行为/处罚/文号/日期/有效期/主体确认/证据）；政府采购网需显示实际导入的证据截图引用；
   未查询/受阻/失败**不等于**“无失信记录”。
10. **人工复核与待补资料**：人工复核必需的发现 + 资料缺口（清单异常、低置信度、
   覆盖缺口、主体未确认、采购条款缺失、无投标截止日）。
11. **附录**：输入文件清单与哈希、版本与规则清单、查询日志摘要、脱敏说明。

## 每条风险明细行的必备字段

`编号`、`风险域`、`预警级别`、`证据强度`、`涉及供应商`、`发现事实`、`规则编号`、
`证据定位`、`查询/采集时间`、`状态`、`建议复核动作`。

## 表述红线

- 不显示完整身份证号、手机号；证件号仅掩码 + 受控摘要；
- 弱线索（META-003、ID-003W、META-001 III）事实文本必须中性
  （“存在弱同源线索……仅作为线索列出”），禁止出现“同一制作方”“串标”“围标”“违法”等断言；
- 查询状态如实展示；不得出现“无失信”“未发现风险”替代未完成查询；
- 所有 I 级与主体歧义项标注“人工复核必需”。

## 渲染前检查（render_report.py 自动执行）

1. Schema 校验：ReportBundle 按 schemas/report-bundle.schema.json 构造，失败即退出；
2. 脱敏检查：对四个验收基准输出扫描完整身份证号/手机号模式（含摘要十六进制串的
   字母数字边界排除），命中即退出码 3 —— **渲染失败好过泄漏**。

## 验收标准（对应方案 9.3）

1. 四类正文（公司交叉、文件属性、司法经营、违法失信）和查询覆盖表均存在；
2. T02、T04、T07 的结果、级别与人工复核要求正确；
3. T03 和 T08 不被表述为违法或串标事实；
4. 任一发现可凭证据 ID 回到证据索引和原始文件定位；
5. 没有完整身份证号、手机号或访问凭证；
6. 无外网或外部凭证时，流程仍能成功输出报告并如实记录未查询来源；
7. 规则等级漂移、未标识查询失败、无法追溯或敏感信息泄露 —— 任一出现即不通过。
